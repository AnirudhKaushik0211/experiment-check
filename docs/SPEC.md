# ExperimentCheck: clean-room build spec

Version 1.0 for app version 1.0.0. Companion to [PRD.md](PRD.md).

This is a clean-room functional and technical description. Everything here comes from public statistical references (section 13) and general web-platform knowledge. All names, numbers and scenarios are synthetic. An implementer should be able to build the app, tests, scripts and README from this document alone, without making architectural decisions. Where the document says MUST, it is a requirement. Where it gives a value, use that value.

## 1. Goals and constraints

- A static, browser-only single page: `index.html` + CSS + plain JavaScript. No server, no build step, zero runtime dependencies, no network requests, no analytics, no external fonts or CDNs.
- It works from GitHub Pages (https) and offline by double-clicking `index.html` (file://) in current Edge, Chrome and Firefox.
- Node.js (22 or newer; development machine has 24) is used only for development tooling: tests, static server, browser smoke test, screenshots and packaging. Node built-ins only. No npm packages, ever.
- The statistics core is pure JavaScript shared by the browser and Node (same files, no copies).
- Statistical honesty: every formula is named and cited in the Guide and README, approximations are labelled, and assumptions and limitations are shown in the app and the memo.
- Clean room: synthetic demo data only. No personal names, employers, internal tool names, real experiment numbers or absolute local paths in any repository file. Enforced by the deny-list scan (section 11.3).

### 2.2 Decision: classic scripts, not ES modules

Browsers load ES modules (`<script type="module">`) in CORS mode. From a file:// page the origin is opaque (`null`), so Chromium-based browsers (Edge, Chrome) refuse module scripts loaded from file://; Firefox behaviour depends on version and settings. That alone breaks double-click use for most visitors. Classic `<script src>` files are not fetched in CORS mode and load from file:// in all three browsers.

So the app uses classic scripts only:

- `index.html` loads, in this order, each with `defer`: `js/stats.js`, `js/format.js`, `js/validate.js`, `js/plan.js`, `js/readout.js`, `js/memo.js`, `js/scenarios.js`, `js/state.js`, `js/ui.js`. Deferred scripts run in document order after parsing, so `ui.js` may start immediately (no `DOMContentLoaded` needed, though listening for it is harmless).
- No `type="module"`, no `import`/`export`, no dynamic `import()`, no `fetch`/`XMLHttpRequest` (file:// fetch is blocked in Chromium). Demo data lives in `js/scenarios.js`, not JSON files.
- Each shared file uses this UMD wrapper. Dependencies come from `require` in Node and from the global namespace in the browser:

```js
(function (root, factory) {
  'use strict';
  var isNode = typeof module === 'object' && module && module.exports;
  var deps = isNode ? { stats: require('./stats.js') } : { stats: root.ExperimentCheck.stats };
  var api = factory(deps);
  if (isNode) module.exports = api;
  else { root.ExperimentCheck = root.ExperimentCheck || {}; root.ExperimentCheck.plan = api; }
})(typeof self !== 'undefined' ? self : this, function (deps) {
  'use strict';
  var stats = deps.stats;
  // ... pure functions only; no DOM, no globals, no Date.now()
  return { /* public API */ };
});
```

Namespaces: `ExperimentCheck.stats`, `.format`, `.validate`, `.plan`, `.readout`, `.memo`, `.scenarios`, `.state`. Dependencies (a module may use only the ones listed):

| Module | Depends on |
|---|---|
| stats | none |
| format | none |
| validate | none |
| plan | stats |
| readout | stats, plan |
| memo | format, plan, readout |
| scenarios | none |
| state | none |
| ui | all |

The `deps` object in each wrapper lists exactly that module's dependencies.
- Syntax: ES2020 at most (no top-level await, no class fields, no `??=`), so the files parse in older evergreen browsers. `var` or `const`/`let` is fine.
- The smoke test MUST confirm that file:// mode works in headless Edge and Firefox (section 10.3, scenarios run in both `file` and `http` modes).

### 2.3 Content Security Policy

`index.html` has this meta tag as the first element in `<head>` after `<meta charset="utf-8">`:

```html
<meta http-equiv="Content-Security-Policy" content="default-src 'none'; script-src 'self' file:; style-src 'self' file:; img-src 'self' data: file:; connect-src 'none'; font-src 'none'; object-src 'none'; base-uri 'none'; form-action 'none'">
```

`file:` is listed because some browsers do not match `'self'` for file:// pages. It has no effect over https. Rules that follow from the policy:

- No inline `<script>` blocks, no `on*=` attributes and no `style="..."` attributes in markup.
- Setting styles via CSSOM (`el.style.x = ...`) and SVG presentation attributes is fine.
- `connect-src 'none'` makes "no network" enforceable.

Deterministic fallback: if, and only if, the smoke test shows that this CSP blocks the app's own scripts or stylesheet under file:// in either browser, remove the meta tag entirely. Record that in the report; the "no network" guarantee then rests on the static test in section 10.1 (`static.test.cjs`) plus the smoke test's network check. Do not try other CSP variants.

A single switch carries the decision through the rest of the project:

- `js/state.js` exports `CSP_META = true`. Set it to `false` only under the fallback above, in the same change that removes the meta tag, and say so in the report.
- `static.test.cjs`: if `CSP_META`, the tag is present and equals the one above exactly; otherwise no `Content-Security-Policy` meta tag exists in `index.html`.
- Smoke S16: the request-origin check always applies; `__smokeCsp === 0` is asserted only if `CSP_META`.
- Public wording (README "Privacy", Guide "Privacy"): if `CSP_META`, "No network requests (blocked by a Content Security Policy and checked by automated tests)."; otherwise "No network requests (the code makes none, which automated tests check)." The Guide text is static HTML, so the implementer writes the matching sentence; `static.test.cjs` asserts that `index.html` contains the sentence that matches `CSP_META` and not the other one.

### 2.4 Data flow

1. The UI keeps one in-memory raw state object (section 7.1). All input values in it are strings, exactly as typed.
2. On any `input`/`change` event (debounced 150 ms):
   - `validate.parsePlan(raw.plan)` -> `plan.computePlan(parsed)`.
   - If the readout has any non-empty field: `validate.parseReadout(raw.readout, parsedPlan)` -> `readout.audit(parsedPlan, planResult, parsedReadout)`.
   - Then `memo.buildPrereg(...)` and `memo.buildMemo(...)`.
   - Then render.
3. The raw state is written to the URL hash (debounced 400 ms, section 7.2).
4. Pure modules never read the clock. The UI passes "today" (local date, `YYYY-MM-DD`) as `generatedOn` to the memo builders.
5. After the first render at startup (defaults, restored hash or defaults after a bad hash), the UI writes the hash once immediately (no debounce, same `replaceState` / `location.replace` rule as 7.2), so `#ec-share-url` is always a complete link.

### 3.2 Tabs (WAI-ARIA tabs pattern, automatic activation)

- Each tab is a `<button role="tab" aria-selected aria-controls>`. Only the selected tab has `tabindex="0"`; the others have `tabindex="-1"`.
- Keys on a tab:
  - Left and Right arrows move to the previous or next tab and select it (wrapping).
  - Home and End select the first and last tab.
  - Enter and Space select the focused tab.
- Hidden panels use the `hidden` attribute.
- Selecting a tab updates `raw.tab` (and therefore the hash).

### 3.3 Which tab opens first

At startup, in this order:

1. If the hash decodes to a valid state, open `state.tab`. If the help-seen flag is not set, show the new-here banner (do not force the Guide).
2. Else if a hash is present but invalid, load the defaults, open Plan, and show the status message "This link could not be read, so the defaults were loaded." (plus the banner if help has not been seen).
3. Else if help has not been seen, open Guide.
4. Else open Plan.

"Help seen" is set (`localStorage.setItem('experimentcheck.helpSeen.v1', '1')`) when the user:

- clicks `#ec-guide-start` ("Start planning", at the top and bottom of the Guide),
- clicks `#ec-newhere-dismiss` or `#ec-newhere-open`,
- selects any non-Guide tab.

All storage access goes through two helpers:

```js
function storageGet(key) { try { return window.localStorage.getItem(key); } catch (e) { return null; } }
function storageSet(key, value) { try { window.localStorage.setItem(key, value); return true; } catch (e) { return false; } }
```

If storage is unavailable (blocked, private mode, or a throwing getter), the app works and treats help as not seen on each visit. It logs nothing and never calls `console.error`. localStorage is used only for this flag. No inputs are stored, which keeps the privacy model simple; the hash is the only state persistence.

### 3.7 Copy, download and print

- Copy:
  1. If `navigator.clipboard && window.isSecureContext`, use `navigator.clipboard.writeText(text)`.
  2. On rejection, or if the API is missing, fall back to selecting the associated textarea and `document.execCommand('copy')` inside try/catch.
  3. On success the status line says "Copied to the clipboard.". On failure it says "Copy did not work in this browser. The text is selected; press Ctrl+C (Cmd+C on a Mac)." and the textarea is focused and selected.
  4. Never `console.error`.

## 4. Numerics (`js/stats.js`)

All functions are pure, take numbers and return numbers, and return `NaN` for invalid arguments. They never throw. The reference values and tolerances are in section 9.

### 4.1 Standard normal

`normUpperAbs(a)` for `a >= 0` (Hart 1968, algorithm 5666, as published by West 2005). It has double-precision absolute accuracy, and the upper tail is computed directly, so small p-values stay precise:

```
function normUpperAbs(a):            // P(Z > a), a >= 0
  if a > 37: return 0
  e = exp(-a*a/2)
  if a < 7.07106781186547:
    n = 3.52624965998911e-2*a + 0.700383064443688
    n = n*a + 6.37396220353165;  n = n*a + 33.912866078383;  n = n*a + 112.079291497871
    n = n*a + 221.213596169931;  n = n*a + 220.206867912376
    d = 8.83883476483184e-2*a + 1.75566716318264
    d = d*a + 16.064177579207;   d = d*a + 86.7807322029461; d = d*a + 296.564248779674
    d = d*a + 637.333633378831;  d = d*a + 793.826512519948; d = d*a + 440.413735824752
    return e * n / d
  b = a + 0.65; b = a + 4/b; b = a + 3/b; b = a + 2/b; b = a + 1/b
  return e / b / 2.506628274631

normCdf(x) = x >= 0 ? 1 - normUpperAbs(x) : normUpperAbs(-x)
normSf(x)  = x >= 0 ? normUpperAbs(x)     : 1 - normUpperAbs(-x)     // upper tail P(Z > x)
```

`normInv(p)` for `0 < p < 1` (Acklam's rational approximation, relative error about 1.15e-9, then one Halley step, which takes it to about 1e-15). `p <= 0`, `p >= 1` and `NaN` return `NaN`.

```
a = [-3.969683028665376e+01, 2.209460984245205e+02, -2.759285104469687e+02, 1.383577518672690e+02, -3.066479806614716e+01, 2.506628277459239e+00]
b = [-5.447609879822406e+01, 1.615858368580409e+02, -1.556989798598866e+02, 6.680131188771972e+01, -1.328068155288572e+01]
c = [-7.784894002430293e-03, -3.223964580411365e-01, -2.400758277161838e+00, -2.549732539343734e+00, 4.374664141464968e+00, 2.938163982698783e+00]
d = [7.784695709041462e-03, 3.224671290700398e-01, 2.445134137142996e+00, 3.754408661907416e+00]
pl = 0.02425
if p < pl:        q = sqrt(-2 ln p);     x =  (((((c0 q+c1)q+c2)q+c3)q+c4)q+c5) / ((((d0 q+d1)q+d2)q+d3)q+1)
elif p <= 1-pl:   q = p-0.5; r = q*q;    x = (((((a0 r+a1)r+a2)r+a3)r+a4)r+a5) q / (((((b0 r+b1)r+b2)r+b3)r+b4)r+1)
else:             q = sqrt(-2 ln(1-p));  x = -(((((c0 q+c1)q+c2)q+c3)q+c4)q+c5) / ((((d0 q+d1)q+d2)q+d3)q+1)
// Halley refinement, using the tail that keeps precision
err = p < 0.5 ? normCdf(x) - p : (1 - p) - normSf(x)
u = err * sqrt(2*pi) * exp(x*x/2)
x = x - u / (1 + x*u/2)
return x
```

### 4.2 Log-gamma, incomplete beta and incomplete gamma

`lnGamma(z)` for `z > 0` uses the Lanczos approximation (g = 7, 9 coefficients). For `z < 0.5` it uses the reflection formula `ln(pi / |sin(pi z)|) - lnGamma(1 - z)`.

```
L = [0.99999999999980993, 676.5203681218851, -1259.1392167224028, 771.32342877765313, -176.61502916214059,
     12.507343278686905, -0.13857109526572012, 9.9843695780195716e-6, 1.5056327351493116e-7]
z = z - 1; s = L[0]; for i in 1..8: s += L[i] / (z + i)
t = z + 7.5
return 0.5 ln(2 pi) + (z + 0.5) ln t - t + ln s
```

`betaInc(a, b, x)` (regularised incomplete beta I_x(a, b); Numerical Recipes `betacf`, modified Lentz, `EPS = 1e-15`, `FPMIN = 1e-300`, at most 300 iterations):

```
if x <= 0: return 0;  if x >= 1: return 1
bt = exp(lnGamma(a+b) - lnGamma(a) - lnGamma(b) + a ln x + b ln(1-x))
return x < (a+1)/(a+b+2) ? bt * betacf(a, b, x) / a : 1 - bt * betacf(b, a, 1-x) / b
```

`gammaQ(a, x)` (regularised upper incomplete gamma; Numerical Recipes `gser`/`gcf`, tolerance 1e-16, at most 1000 iterations):

- `x <= 0`: return 1.
- `x < a + 1`: `1 - P(a, x)` from the series `P = e^{-x} x^a / Gamma(a) * sum_{n>=0} x^n / (a (a+1) ... (a+n))`.
- Otherwise: the Lentz continued fraction for Q.

### 4.3 Student t

```
tSf(t, df):                       // P(T > t), df > 0
  if df > 1e7: return normSf(t)
  x = df / (df + t*t)
  tail = 0.5 * betaInc(df/2, 0.5, x)
  return t >= 0 ? tail : 1 - tail
tCdf(t, df) = 1 - tSf(t, df)
tInv(p, df):                      // 0 < p < 1
  if df > 1e7: return normInv(p)
  if p == 0.5: return 0
  if p < 0.5: return -tInv(1 - p, df)
  target = 1 - p; lo = 0; hi = 1
  while tSf(hi, df) > target: hi = hi * 2        // at most 60 doublings, else NaN
  repeat up to 200 times:
    mid = (lo + hi)/2
    if tSf(mid, df) > target: lo = mid else: hi = mid
    stop when hi - lo < 1e-13 * max(1, hi)
  return (lo + hi)/2
```

Non-integer `df` (Welch) is supported.

### 4.4 Chi-square

`chiSquareSf(x, df) = gammaQ(df/2, x/2)` for `x >= 0` and `df > 0`. With 2 arms, `df = 1`, and the result equals `2 * normSf(sqrt(x))`; the tests check that the two agree.

## 5. Plan calculations (`js/plan.js`)

### 5.1 Parsed plan (output of `validate.parsePlan`)

```
{ name, metricName, type: 'binary'|'continuous', dir: +1|-1,       // +1 = higher is better
  p1 (binary, fraction), mean, sd (continuous),
  mdeType: 'relative'|'absolute', mde (relative: fraction of baseline; absolute: fraction for binary, units for continuous),
  alpha (fraction), power (fraction), sides: 1|2, share (treatment fraction), daily (int), start ('YYYY-MM-DD'|null),
  hypothesis, notes, guardrails: [{ id, name, type, dir: +1|-1, margin (fraction) }] }
```

### 5.2 Effect to detect

```
mdeAbs = mdeType == 'relative' ? mde * baseline : mde      // baseline = p1 (binary) or mean (continuous)
// binary baseline is always > 0. A continuous mean may be 0 or negative, but only with an absolute MDE (validation 8.2)
baselinePositive = type == 'binary' || mean > 0
mdeRel = baselinePositive ? mdeAbs / baseline : NaN         // format.pct(NaN) and format.spct(NaN) print 'n/a'
target = baseline + dir * mdeAbs                            // binary: must be strictly between 0 and 1 (validation)
za = normInv(1 - alpha / sides);  zb = normInv(power);  k = share / (1 - share)   // n_treatment = k * n_control
```

### 5.3 Sample size, binary: two-proportion test, normal approximation

This is the formula in Fleiss, Levin and Paik (2003), ch. 4 (sample size for two independent proportions, including unequal allocation), without the continuity correction. Cite the chapter, not an equation number; the equation number was not checked against the book: pooled variance under H0 and unpooled under H1. With `k = 1` it equals R's `power.prop.test` (default `strict = FALSE`).

```
p2 = target; pbar = (p1 + k*p2) / (1 + k); qbar = 1 - pbar
n1 = ( za*sqrt(pbar*qbar*(1 + 1/k)) + zb*sqrt(p1*(1-p1) + p2*(1-p2)/k) )^2 / (p2 - p1)^2
```

### 5.4 Sample size, continuous: two-sample means, normal approximation, equal SD

Chow, Shao and Wang (2008), section 3.2, using the normal quantile instead of t:

```
n1 = (1 + 1/k) * sd^2 * (za + zb)^2 / mdeAbs^2
```

This is labelled in the UI as "normal approximation; about 1-2 users per arm fewer than an exact t-based calculation at small n". Example: R's `power.t.test(delta = 1, sd = 1, power = .9)` gives 22.02 per arm, and this formula gives 21.01, which rounds up to 22.

### 5.5 Rounding, totals, duration and advice

```
nControl = ceil(n1 - 1e-9); nTreatment = ceil(k*n1 - 1e-9); total = nControl + nTreatment
rawDays = total / daily
daysNeeded = ceil(rawDays - 1e-9)
recommendedDays = max(7, 7 * ceil(daysNeeded / 7)); weeks = recommendedDays / 7
plannedEnd = start ? addDays(start, recommendedDays - 1) : null        // last day of data, UTC date arithmetic
```

- Infeasible: if `n1` is not finite or `nControl > 1e12`, the plan result is `{ok: false, reason: 'infeasible'}`. The UI says: "This MDE is too small to detect with any realistic sample. Increase the MDE."
- If `rawDays > 3650`, the advice adds: "That is more than 10 years of traffic. Increase the MDE or the traffic."
- Advice paragraphs (`#ec-out-advice`), in this order, each only when its condition holds:
  1. Always: "Run whole weeks so every weekday is represented equally, and at least 7 days to dampen novelty effects."
  2. `daysNeeded < 7`: "The sample needs only {daysNeeded} day(s) of traffic, but run 7 days anyway so every weekday is covered."
  3. `daysNeeded >= 7` and `daysNeeded % 7 != 0`: "{daysNeeded} days of traffic rounds up to {recommendedDays} days ({weeks} full weeks)."
  4. `recommendedDays > 56`: "This is a long test (over 8 weeks). Consider a larger MDE, more traffic or a more sensitive metric; long tests suffer from cookie churn and seasonality."
  5. `share != 0.5`: "An uneven split needs more users in total than 50/50 for the same power."
  6. Continuous and `min(nControl, nTreatment) < 30`: "Small sample: the normal approximation behind this plan is optimistic below about 30 users per arm."
  7. `sides == 1`: "A one-sided test can only show an improvement. A harmful effect will read as 'not significant', so watch the guardrails."

### 5.6 Detectable MDE for a given sample (sensitivity and sample shortfall)

`mdeForSample(plan, nControl)`, where `k` comes from the plan share and `nTreatment = k * nControl`:

- Continuous (closed form): `mdeAbs = (za + zb) * sd * sqrt(1/nControl + 1/(k*nControl))`.
- Binary (bisection on the effect size):

```
hi = (dir > 0 ? 1 - p1 : p1) - 1e-9; lo = 0
need(D) = n1 from 5.3 with p2 = p1 + dir*D
if nControl < 1 or need(hi) > nControl: return NaN          // not detectable at any effect size
repeat 200 times: mid = (lo+hi)/2; if need(mid) > nControl: lo = mid else hi = mid
return hi
```

- `mdeRel = baselinePositive ? mdeAbs / baseline : NaN` (same rule as 5.2).

When `baselinePositive` is false, everything that would show a relative MDE uses the absolute one instead:

- Sensitivity table: the "Detectable MDE (relative)" cells show "n/a".
- Chart: absolute y axis (3.8).
- Pre-registration and memo: the " ({pct(mdeRel)} relative)" part is omitted (8.3).
- Readout `sample` WARN: the detectable and planned MDEs are given in metric units (6.7).

Sensitivity rows: durations `[7, 14, 21, 28, 42, 56, 84]` days. For each `d`, `users = d * daily`, `nC = floor(users * (1 - share))`, `nT = floor(users * share)`, and `mdeAbs = mdeForSample(plan, nC)`. Each row is `{days, weeks, nC, nT, mdeAbs, mdeRel, isPlan: d == recommendedDays}`. If `recommendedDays` is not in the list, the table gets one extra row for it, inserted in order and marked "(plan)". Display "not detectable" for NaN.

## 6. Readout statistics and verdict (`js/readout.js`)

### 6.1 Parsed readout (output of `validate.parseReadout`)

```
{ control: {n, x} | {n, mean, sd}, treatment: same, through: 'YYYY-MM-DD'|null, looks: int, srmThreshold,
  guardrails: { [gid]: { state: 'empty' } | { state: 'ok', control: {...}, treatment: {...} } } }
```

### 6.2 Confidence level

The primary metric interval uses `zc = normInv(1 - alpha/2)` for a two-sided test and `zc = normInv(1 - alpha)` for a one-sided test. A one-sided test therefore shows a two-sided 1-2·alpha interval (90% at alpha = 5%), whose "better" bound equals the one-sided bound. The UI labels the interval with its level, for example "95% CI" or "90% CI".

Guardrails always use the two-sided `1 - alpha` interval.

### 6.3 Binary primary: two-proportion z-test

The test uses the pooled SE. The CI uses the unpooled (Wald) SE. Relative lift uses the log risk ratio (Katz et al. 1978).

```
p1 = xc/nc; p2 = xt/nt; diff = p2 - p1
pp = (xc + xt)/(nc + nt); se0 = sqrt(pp(1-pp)(1/nc + 1/nt))
if se0 == 0: computable = false (reason 'no-variance'); p = NaN
z = diff / se0
p = sides == 2 ? 2*normSf(|z|) : normSf(dir*z)
se = sqrt(p1(1-p1)/nc + p2(1-p2)/nt); ci = [diff - zc*se, diff + zc*se]
relative (only if xc > 0 and xt > 0): rel = p2/p1 - 1
  lse = sqrt((1-p1)/xc + (1-p2)/xt); relCi = [exp(ln(p2/p1) - zc*lse) - 1, exp(ln(p2/p1) + zc*lse) - 1]
else rel = NaN, shown as "n/a (needs at least one conversion in each arm)"
```

### 6.4 Continuous primary: Welch's t-test

Welch (1947), with Welch-Satterthwaite degrees of freedom. Relative lift uses the delta method (approximate, labelled).

```
vc = sdc^2/nc; vt = sdt^2/nt; se = sqrt(vc + vt); diff = mt - mc
if se == 0: computable = false ('no-variance')
t = diff/se; df = (vc + vt)^2 / (vc^2/(nc-1) + vt^2/(nt-1))
p = sides == 2 ? 2*tSf(|t|, df) : tSf(dir*t, df)
tc = tInv(sides == 2 ? 1 - alpha/2 : 1 - alpha, df); ci = [diff - tc*se, diff + tc*se]
relative (only if mc > 0): rel = mt/mc - 1
  rse = sqrt(sdt^2/(nt*mc^2) + mt^2*sdc^2/(nc*mc^4)); relCi = [rel - zc*rse, rel + zc*rse]
```

If `vc` and `vt` are both 0, `df` is undefined; that case is already `no-variance`.

### 6.5 Direction-adjusted effect

`e = dir * diff`, and `[lo, hi] = dir > 0 ? [ci0, ci1] : [-ci1, -ci0]`. So "positive is good" everywhere in the verdict logic. `m = plan.mdeAbs`.

`readout.js` defines the MDE comparison once and uses it in both the `practical` check (6.7) and `primaryCall` (6.8):

```
function meetsMde(e, m) { return e >= m - 1e-12; }   // tolerance absorbs floating-point error at e == m
```

### 6.6 SRM: chi-square goodness-of-fit

```
N = nc + nt; ec = N*(1-share); et = N*share
chi2 = (nc-ec)^2/ec + (nt-et)^2/et; p = chiSquareSf(chi2, 1)
FAIL if p < srmThreshold (default 0.001)
```

A strict threshold such as 0.001 is common practice for SRM alerts, because the check runs on every test and should rarely fire by chance (see Kohavi, Tang and Xu 2020, ch. 21; Fabijan et al. 2019). The docs present 0.001 as a convention, not as a value prescribed by either source.

### 6.7 Timing, peeking, duration, sample and assumption checks

- `plannedEnd` comes from the plan. `observedDays = through - start + 1` (when both are known).
- `early = through != null && plannedEnd != null && through < plannedEnd`.
- Information fraction: `tInfo = min(1, (nc + nt) / plan.total)`.
- O'Brien-Fleming-type spending (Lan and DeMets 1983). Informational only, never used in the verdict, and shown only when `early || looks > 1`:

```
alphaSpent(tInfo) = 2 - 2*normCdf(normInv(1 - alpha/2) / sqrt(tInfo))
```

  Text: "Informational, approximate: an O'Brien-Fleming-type plan (Lan-DeMets spending) would allow about {alphaSpent, 4 dp} of the {alpha} at this point (information fraction {tInfo, 2 dp}). The observed p = {p} {would|would not} cross it{suffix}. This only applies if such a plan was set before the test."

  `{suffix}` is empty when `looks == 1`, and " (exact at a first interim look; at later looks the true boundary is stricter)" when `looks > 1`. "Would cross" means `p < alphaSpent`.
- Repeated-looks false-positive rate (Armitage, McPherson and Rowe 1969; tabulated in Jennison and Turnbull 2000, table 1.1). Use it only when `alpha == 0.05` and `sides == 2`:

| Looks | 1 | 2 | 3 | 4 | 5 | 10 | 20 | 50 | 100 |
|---|---|---|---|---|---|---|---|---|---|
| Overall false-positive rate | 0.05 | 0.083 | 0.107 | 0.126 | 0.142 | 0.193 | 0.248 | 0.320 | 0.374 |

  For a count between table entries, say "between {lower} and {upper}". Above 100, say "above 0.374". With other alpha or sides, say "higher than alpha".

  (A Monte Carlo check during spec writing reproduced 0.084, 0.107, 0.127, 0.141, 0.193 and 0.248 for 2, 3, 4, 5, 10 and 20 looks.)

| Id | Label | Rule |
|---|---|---|
| `srm` | Sample ratio (SRM) | PASS if `p >= threshold`, else FAIL. Detail: "Expected {ec}/{et} at {100(1-share)}/{100 share}; observed {nc}/{nt}; chi-square = {chi2, 2 dp}, p = {p} (alert below {threshold})." |
| `timing` | Timing / peeking | FAIL if `early`: "Analysed on day {observedDays} of {recommendedDays} (data through {through}; planned end {plannedEnd})." When `looks > 1`, append " {looks} looks so far; the false-positive rate is about {fpr} instead of {alpha} if any look could have stopped the test." Else PASS "{D} days ({D/7} full weeks)." |
| `sample` | Sample size | ratio = `(nc+nt)/plan.total`. If below 0.9: WARN "{N} of {plan.total} planned users ({pct(ratio, 0)}). At this sample the test can detect about {D} (planned {P})." Here `{D}` = `mdeForSample(plan, nc)` and `{P}` = the plan MDE, both as `pct(mdeAbs / baseline)` + " relative" when `baselinePositive`, otherwise as `num(mdeAbs)` + " units"; if `{D}` is NaN it reads "no effect of any size". Else PASS "{N} of {plan.total} planned users ({pct(ratio, 0)})." |
| `assumptions` | Approximation | Binary: WARN if any of `xc, nc-xc, xt, nt-xt < 10`: "Fewer than 10 events or non-events in an arm: the normal approximation is unreliable. Continuous: WARN if `min(nc, nt) < 30`: "Fewer than 30 users in an arm: the t-test is sensitive to skewed data at this size." Else PASS "Normal approximation reasonable (at least 10 events and non-events per arm)." or "... (at least 30 users per arm)." |
| `significance` | Statistical significance | INFO: "{pText} vs alpha {num(alpha)} ({two-sided|one-sided}): {significant|not significant}." If not computable: INFO "Not computable: no variation in the data." |
| `practical` | Practical significance | Not computable: INFO "Not computable." `meetsMde(e, m)`: PASS "Observed effect {e} is at least the MDE {m}." Significant and `hi < m`: WARN "Whole CI is below the MDE {m}." Significant otherwise: WARN "Point estimate {e} is below the MDE {m}." Not significant and `hi < m`: INFO "CI upper bound {hi} is below the MDE {m}: a meaningful improvement is ruled out." Not significant otherwise: INFO "CI still includes the MDE {m}." |
| `guardrail:<gid>` | Guardrail: {name} | Section 6.9. |

Values in check text are formatted per section 6.11, always as `{e}` in the metric's units (pp for binary).

### 6.8 Verdict

```
primaryCall(primary, m, alpha, sides):
  if not primary.computable: return ('inconclusive', 'no-variance')
  sig = primary.p < alpha
  if sig and e < 0:                         return ('dont-ship', 'harm')        // two-sided only in practice
  if sig and e > 0:
    if lo <= 0:                             return ('inconclusive', 'borderline') // pooled test vs Wald CI disagree
    if meetsMde(e, m):                      return ('ship', 'ship-meaningful')
    if hi < m:                              return ('dont-ship', 'trivial')
    return ('inconclusive', 'below-mde')
  if hi < m:                                return ('dont-ship', 'flat')
  return ('inconclusive', 'underpowered')

decide(planParsed, planResult, ro):
  // "plan invalid" = parsePlan(...).ok === false OR computePlan(...).ok === false (includes 'infeasible', 5.5);
  // in the infeasible case the readout shows the 5.5 infeasible message instead of "Complete the plan first..." (3.6)
  if plan invalid or readout invalid or readout empty: verdict 'none' (no reasons; the error lists explain)
  checks = [srm, timing, duration, sample, assumptions, significance, practical, guardrails...]
  pc = primaryCall(...)
  if srm.status == FAIL:                    verdict = 'investigate', decisive = 'srm'
  elif any guardrail status FAIL:           verdict = 'dont-ship',   decisive = 'guardrail-breach'
  elif early:                               verdict = 'inconclusive', decisive = 'early'
  else:                                     verdict = pc.verdict,    decisive = pc.reason
```

Reasons list (`reasons: [{id, status, text}]`), in this order:

1. The decisive reason (`status: 'decisive'`).
2. Every other FAIL check, then every WARN check, in check order. Skip the check that produced the decisive reason: `srm` for `srm`, `timing` for `early`, and the first breached guardrail for `guardrail-breach` (later breached guardrails are still listed). Their ids are:
   - `timing`: `looks` for the looks WARN, `dates-missing` for the dates WARN
   - `duration`: `short-duration` or `partial-week`
   - `sample-shortfall`
   - `small-counts` or `small-n`
   - `guardrail-at-risk`, `guardrail-missing`, `guardrail-na`
   - additional breached guardrails (each as `guardrail-breach`)
   - `timing` FAIL that is not decisive (an early analysis when SRM or a guardrail breach decided): `early`, with the check-derived text rule below (not the decisive `early` text from the table)
   - The `significance` and `practical` checks never produce reasons, whatever their status. Their content is already in the decisive reason (from `primaryCall`) or in the `primary-only` reason.
   - INFO and PASS checks never produce reasons.

   The `text` of a check-derived reason is `{check label}: {check detail}`. Additional breached guardrails instead use the `guardrail-breach` reason text from the table below.

   Fixed outcomes (asserted in `verdict.test.cjs`, ids in order):
   - `clean-win`: `['ship-meaningful']`
   - `flat`: `['underpowered']`
   - `trivial`: `['trivial']` (the `practical` WARN adds nothing)
   - `srm`: `['srm', 'primary-only']`
   - `peeking`: `['early', 'short-duration', 'sample-shortfall', 'primary-only', 'obf']` (the three looks are part of the timing check, which is the decisive one and is skipped, so there is no separate `looks` reason)
   - `guardrail-breach`: `['guardrail-breach', 'primary-only']`
   - Synthetic SRM plus early (plan P14 without guardrails; readout n 5800 / 5210, x 580 / 600, through 2025-03-07, looks 1): `['srm', 'early', 'short-duration', 'sample-shortfall', 'primary-only', 'obf']`
3. If the decisive reason is not from `primaryCall` and the primary is computable: `{id: 'primary-only', status: 'info', text: 'Primary metric on its own: {label of pc.verdict}. {primary reason text}'}`.
4. If `early` or `looks > 1`, the OBF informational text as `{id: 'obf', status: 'info'}`.

Labels: `ship` "Ship"; `dont-ship` "Don't ship"; `inconclusive` "Inconclusive - extend"; `investigate` "Investigate (SRM)"; `none` "No verdict yet".

Decisive reason texts (`text`), summaries (`#ec-verdict-summary`) and next steps (`#ec-verdict-next`):

| Decisive id | Reason text | Summary | Next step |
|---|---|---|---|
| `srm` | "Sample ratio mismatch: p = {p} is below the {threshold} alert threshold (expected {ec}/{et}, observed {nc}/{nt})." | "The traffic split does not match the plan, so the results can't be trusted yet." | "Find the cause before reading any metric: check assignment, redirects, bot filtering, logging and eligibility rules. Re-run after fixing it." |
| `guardrail-breach` | "Guardrail breached: {name} got {d} worse (limit {margin})." | "A guardrail got worse by more than its pre-registered limit." | "Do not roll out as is. Fix the guardrail regression, then re-test." |
| `early` | "Analysed early: data through {through}, planned end {plannedEnd} (day {D} of {R})." | "The test was analysed before its planned end, so the result isn't final." | "Keep the test running until the planned end date, then analyse once." |
| `ship-meaningful` | "Primary metric improved by {e} ({pText}), at least the MDE of {m}." | "The primary metric improved by at least the MDE, and the result is statistically significant." | "Roll out, and keep watching the guardrails after launch." |
| `trivial` | "Primary metric improved by {e} ({pText}), but the whole {level} CI ({lo} to {hi}) is below the MDE of {m}." | "The improvement is real but smaller than the MDE." | "Ship only if the change costs nothing to keep; otherwise drop it and test a bolder idea." |
| `below-mde` | "Primary metric improved by {e} ({pText}); the point estimate is below the MDE of {m}, but the CI reaches {hi}." | "The improvement is significant, but it may be smaller than the MDE." | "Extend the test or re-run it with more users to pin down the size of the effect." |
| `borderline` | "The p-value ({pText}) and the {level} CI ({lo} to {hi}) disagree at the edge of significance." | "The result sits right at the edge of significance." | "Extend the test to get a clearer answer." |
| `harm` | "Primary metric got worse by {abs e} ({pText})." | "The primary metric got significantly worse." | "Do not roll out. Learn from the result and iterate." |
| `flat` | "No significant effect ({pText}); the {level} CI ({lo} to {hi}) rules out an improvement as large as the MDE of {m}." | "No meaningful effect: the data rule out an improvement as large as the MDE." | "Stop here. Do not roll out; test a different idea." |
| `underpowered` | "No significant effect ({pText}), and the {level} CI ({lo} to {hi}) still includes the MDE of {m}." | "The test can't tell yet whether there is a meaningful effect." | "Extend the test, or re-plan with the observed numbers, a larger MDE or more traffic." |
| `no-variance` | "The primary metric has no variation in either arm, so no test can be computed." | "The data show no variation." | "Check that the numbers were entered correctly." |

In this table, `{e}`, `{lo}`, `{hi}` and `{m}` are direction-adjusted (positive is good) and formatted as signed metric units (for example "+1.40 pp" or "+2.00"); `{level}` is "95%" or "90%"; and `{pText}` is "p < 0.0001" or "p = 0.013".

Rationale and citation: this is the statistical-versus-practical-significance grid from Kohavi, Tang and Xu (2020), ch. 2 (the end-to-end example chapter, which closes with example significance outcomes and launch decisions), made explicit. If the implementer cannot confirm the chapter, cite the book without a chapter rather than guess. SRM comes first because an SRM invalidates every metric (Fabijan et al. 2019). Guardrails come before the primary metric because a breach blocks shipping however good the primary is. An early analysis can't produce a final decision, because repeated looks inflate the false-positive rate (Armitage et al. 1969).

### 6.9 Guardrails

For each plan guardrail `g` (with `dir` and `margin`), and with `z = normInv(1 - alpha/2)`:

- `state == 'empty'`: WARN `guardrail-missing`, detail "No data entered."
- Binary: Katz relative change as in 6.3. If `xc == 0` or `xt == 0`: WARN `guardrail-na` "Relative change can't be computed with zero events in an arm."
- Continuous: delta-method relative change as in 6.4 (with `z`). If the control mean is 0 or less: WARN `guardrail-na` "Relative change needs a positive control mean."
- Degradation (positive means worse): `deg = -g.dir * rel`. Worse bound: `worst = g.dir > 0 ? -relCi[0] : relCi[1]`.
- Status:
  - FAIL (`guardrail-breach`) if `deg > margin`: the point estimate is worse than the limit.
  - WARN (`guardrail-at-risk`) if `deg <= margin < worst`: within the limit, but not shown to be.
  - PASS otherwise.
- Where the rule sits: it lies between two formal tests. It is stricter than a harm test (block only when the whole CI is beyond the limit) and less strict than a non-inferiority test (ship only when the whole CI is within the limit). It blocks on the point estimate and marks "At risk" when the CI reaches past the limit, because guardrails are usually underpowered and a non-inferiority requirement would block most tests. The Guide and README state this in these words; never call the rule "conservative".
- Detail: "Change {signed rel %} ({95%} CI {signed lo %} to {signed hi %}); {higher|lower} is better; limit {margin %} worse. {Breached.|At risk: the CI reaches {worst %} worse.|Within the limit.}"
- No multiple-comparison correction is applied across guardrails (stated in limitations).

### 6.10 Assumptions and limitations (shown in the Guide, the README and every memo)

- Users are randomised independently, the analysis unit equals the randomisation unit, and each user is counted once.
- Normal approximations: z-test, Wald CI and Katz log CI (binary); delta-method relative CI (continuous); normal-approximation sample size. They are unreliable with small counts, and the tool warns.
- Welch's t-test assumes approximately normal sample means (central limit theorem). Heavily skewed metrics (revenue) may need more data or a transformation.
- One treatment vs one control. No correction for multiple metrics or multiple guardrails.
- No valid sequential testing: peeking is only warned about. The O'Brien-Fleming figure is informational.
- The verdict is a documented rule, not a substitute for judgement about costs, risks and strategy.
- Daily traffic is assumed constant. Returning users make the real duration longer.

### 6.11 Formatting (`js/format.js`)

All formatting is locale-independent (`en-US` grouping), and every negative number uses ASCII `-`. `-0` is printed as `0`. `NaN` and non-finite values print as `n/a` in every function.

Sign rule for the signed functions (`spct`, `pp`, `snum`): round to the display precision first, then choose the sign from the rounded value. So -0.00001 with `spct` prints "+0.00%", never "-0.00%".

| Function | Rule | Example |
|---|---|---|
| `int(n)` | `Math.round(n).toLocaleString('en-US')` | `15,400` |
| `pct(f, d=2)` | `(100f).toFixed(d) + '%'` with grouping | `10.00%` |
| `spct(f, d=2)` | signed pct: `+` for > 0, `-` for < 0, `+` for 0 | `+14.04%` |
| `pp(f, d=2)` | signed percentage points: `spct` without `%`, + `' pp'` | `+1.40 pp` |
| `ppAbs(f)` | unsigned pp | `1.00 pp` |
| `num(x)` | if `abs(x) >= 1e5`: `Math.round(x)` with grouping. Otherwise `x.toPrecision(6)`, converted back to plain decimal notation (no exponent), trailing zeros and a trailing `.` trimmed, then grouping of the integer part | `1,205`, `0.0345`, `1,234,567`, `12,345.7` |
| `snum(x)` | signed `num` | `+2`, `-0.5` |
| `pValue(p)` | `< 0.0001` if p < 0.0001; `toFixed(4)` if p < 0.01; else `toFixed(3)`; `n/a` for NaN | `0.0072`, `0.013` |
| `pText(p)` | `'p < 0.0001'` or `'p = ' + pValue(p)` | `p = 0.909` |
| `stat(x)` | `toFixed(2)` | `3.99` |
| `df(x)` | `toFixed(1)` | `725.3` |

Effect units: binary effects and MDEs use `pp`, continuous ones use `snum`. Relative values use `spct`. Rates use `pct`.

Field details:

- Plan guardrail: `{ "id": "g1", "name": "", "type": "binary"|"continuous", "direction": "decrease"|"increase", "margin": "5" }`. A new row has type `binary`, direction `decrease` and margin `5`.

  - every numeric field: 32

### 7.2 URL hash

- Format: `#s=<base64url(UTF-8 JSON of the raw state)>`, with no padding (`+` -> `-`, `/` -> `_`, `=` stripped). Encode with `TextEncoder` and `btoa` over the byte string, and decode with `atob` and `new TextDecoder('utf-8', {fatal: true})`. All of these are globals in browsers and Node 22+, so `state.js` stays testable in Node.
- `state.encode(raw)` returns the hash string including `#s=`.
- `state.decode(hash)` returns `{ok: true, state}` or `{ok: false, error}`, and never throws. `error` is one of:
  - `empty`: no hash, or `#`
  - `format`: does not start with `#s=`
  - `too-long`: over 64,000 characters (the worst case allowed by the 7.1 limits is about 46,500 characters: lone UTF-16 surrogates such as U+D800 are not control characters, so `sanitize` keeps them, and `JSON.stringify` writes each one as the 6-byte escape `\ud800`; for comparison, "测" fills give about 24,800 and `"` or `\` fills about 17,500. `sanitize` does not replace lone surrogates; the 64,000 limit covers them)
  - `base64`
  - `utf8`
  - `json`
  - `version`: `v` is not 1
- `state.sanitize(obj)` builds a fresh default state and copies over only known keys with the right types:
  - Control characters are removed first: in `hypothesis` and `notes`, every character in U+0000-U+001F and U+007F except `\n`; in every other string field, all of them (including `\n`). Then strings are truncated to their maximum length. Wrong types, and enum values outside the allowed set, keep the default.
  - The UI applies the same `sanitize` to its raw state before every encode, so what is written is always decodable.
  - Plan guardrails: an array of at most 10 objects. Ids must match `^g[1-9][0-9]{0,3}$` and be unique; otherwise the row gets a fresh id (the next unused `gN`).
  - Readout guardrails: kept only for ids present in the plan guardrails.
  - Unknown keys are dropped. Prototype keys (`__proto__`, `constructor`, `prototype`) are never copied: iterate with `Object.keys` over a JSON-parsed object, and assign into objects created with `Object.create(null)`, then copy into plain objects.
- Writing: once after the first render at startup (2.4 step 5), then after every state change (debounced 400 ms): `h = state.encode(state.sanitize(raw))`, then `lastHash = h` (set before writing, so a `hashchange` fired by the fallback is ignored), then `try { history.replaceState(null, '', h) } catch { location.replace(h) }`, then update `#ec-share-url`. Do not push history entries.
- If `h.length > 64000` (not reachable within the 7.1 limits; defensive), still write it, and the status line says "The share link is too long to reopen; shorten the hypothesis or notes."
- Reading: at startup, and on `hashchange` when `location.hash !== lastHash`: decode, and on success replace the state, re-render, and show the status message "Loaded the inputs from the link." On failure, keep the current state and show "This link could not be read, so nothing was changed." (The startup case is in 3.3.)
- Privacy note (shown in the Guide): browsers never send the `#...` part to a server, but anyone with the link can read the inputs.

### 8.3 Documents (`js/memo.js`)

A document is `{ title, blocks: [...] }`, where each block is one of:

- `{type: 'h1'|'h2'|'p'|'strong-p', text}`
- `{type: 'ul', items: [text]}`
- `{type: 'table', header: [text], rows: [[text]]}`

`strong-p` is a paragraph whose first part is bold: `{type: 'strong-p', strong, text}`.

`memo.toMarkdown(doc)`:

- Blocks are separated by one blank line, and the output ends with a single newline.
- `h1` -> `# text`, `h2` -> `## text`, `p` -> `text`, `strong-p` -> `**strong** text`, `ul` -> `- item` lines.
- `table` -> a pipe table, with a `|---|` separator per column.
- Inside table cells, `|` is escaped as `\|` and newlines become spaces.
- User text (name, metric name, hypothesis, notes, guardrail names) has control characters other than `\n` removed. Single-line fields have newlines replaced by spaces.

The UI renders the same blocks to DOM elements (`h1`, `h2`, `p`, `strong`, `ul/li`, `table/thead/tbody`) with `textContent`.

`memo.buildPrereg({plan, planResult, srmThreshold, version, generatedOn})` produces exactly this structure (braces are values, `|` inside braces separates alternatives, and square brackets mark optional parts: `week[s]` is plural when weeks != 1, and the relative-MDE brackets are explained below the memo template):

```
# Pre-registration: {name}

Prepared {generatedOn} with ExperimentCheck {version}. Agree on this before the test starts, and don't change it afterwards.

## Hypothesis

{hypothesis | Not written yet.}

## Primary metric
```

### 11.2 Output

- Defaults: `dist/experiment-check-public/` (a copy of the allow-listed files) and `dist/experiment-check-public.zip`. `--out <dir>` overrides the folder; the zip is always `<out>.zip`.
- The script refuses (exit 1) when:
  - `--out` contains the project folder, or
  - `--out` exists and is not a previous package (a previous package is recognised by containing `index.html` and `js/stats.js`).
- The zip is written by `scripts/zip.cjs`:
  - deflate via `zlib.deflateRawSync`, or stored if that is not smaller
  - own CRC-32 table
  - UTF-8 flag (bit 11) set
  - fixed DOS timestamp 2025-01-01 00:00, so zips are reproducible
  - entry names `experiment-check-public/<relative path>` with forward slashes only
  - no directory entries, no ZIP64 (refuse if there are more than 65,535 entries or more than 4 GB)
  - Never use .NET `ZipFile.CreateFromDirectory` or PowerShell `Compress-Archive` (backslash entry names on some versions).
- After writing, the script reads the zip back and verifies:
  - the entry count equals the file count
  - no entry name contains a backslash
  - every entry inflates to bytes identical to the copied file

### 11.3 Deny-list scan (`scripts/denylist.cjs`, module and CLI)

Two sources of patterns:

1. Generic patterns, which are public and always on:
   - Windows profile paths: `/[A-Za-z]:[\\/]+Users[\\/]+/i`
   - macOS and Linux home paths: `/\/Users\/[^\/\s]+\//` and `/\/home\/[^\/\s]+\//`
   - e-mail addresses: `/[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}/`
2. Private terms:
   - The owner's file `.denylist.local` at the project root: UTF-8, one term per line, `#` starts a comment, blank lines are ignored. It is gitignored and never packaged.
   - Plus the environment variable `EXPC_DENY_EXTRA` (comma-separated).
   - The private term list is supplied by the repository owner out of band. It is deliberately not written in any repository file, not even encoded. The implementer creates `.denylist.local` from the owner's brief.

Term matching:

- Case-insensitive.
- Within a term, any run of space, `_` or `-` matches any run of `[\s_-]*`.
- Every other character is matched literally, with regex escaping.
- Short terms (3 characters or fewer, or 4 characters or fewer that contain a digit) must not have letters or digits on either side: `(?<![A-Za-z0-9])term(?![A-Za-z0-9])`.
- Longer terms match anywhere as substrings, so a name inside a longer identifier is still caught.

Scanned: every file and folder name (relative path, with both `/` and `\` forms), plus file content by type. Compressed or pixel bytes are never scanned as text, because random bytes produce chance matches for short terms (about one per MB was measured on a comparable package):

- Text types (`.html .css .js .cjs .json .md .txt .svg`, the root dotfiles `.gitignore` and `.nojekyll`, and `LICENSE`): UTF-8 content, line by line. Invalid UTF-8 is a hit ("undecodable text").
- `.png`: parse the chunk list (8-byte signature, then repeated length / type / data / CRC; stop at `IEND`).
  - Scan the chunk type names.
  - Scan the text of `tEXt` chunks (Latin-1 keyword and text), `zTXt` chunks (keyword, then the inflated text), `iTXt` chunks (keyword, language tag, translated keyword and text, inflating the text when the compression flag is 1; UTF-8) and `eXIf` chunks (as Latin-1).
  - Never scan `IDAT` or any other chunk payload.
  - If the signature is wrong, a length runs past the end of the file, inflation fails or there is no `IEND`, the file is a hit ("unparseable binary").
  - The capture script writes PNGs from the browser's screenshot data unchanged; Chromium adds no text chunks, so a clean PNG has nothing to scan except chunk types.
- `.zip`: scan every entry name, then apply these same per-type rules to each inflated entry according to its extension. Never scan the raw (compressed) zip bytes.
- Any other extension (or a file without one that is not in the text list): the scan refuses (a hit, "unsupported file type"). The allow-list (11.1) only admits the types above.

Pixel content is covered by the capture script's visible-text scan (10.4) and the human check of every image.

Output lists `file:line [N chars]` (text), `file:chunk <type> [N chars]` (PNG) or `zip!entry:...` (inside the zip), and never prints the matched term. The CLI is `node scripts/denylist.cjs [dir] [--generic-only]`, with exit code 0 for no hits and 1 for hits.

Test files must never contain trigger strings literally. Build them at runtime by concatenation (for example `'someone' + '@' + 'example.com'`, `'C:' + '\\' + 'Users' + '\\'`), so the package scan of `test/` stays clean.

Flags on `package-public.cjs`:

- `--require-local`: fail (exit 1) if `.denylist.local` is missing. This is the owner's mode, and `npm run package` uses it.
- `--generic-only`: scan only the generic patterns (for other people who clone the repository).
- Neither flag: use `.denylist.local` if it is present; if it is missing, print "WARNING: no .denylist.local; only generic patterns were scanned." and continue.

Scope: the deny-list scan runs over the output folder and then over the zip. Any hit removes both outputs and exits 1.

Console output (one line each): allow-listed file count, path problems, deny-list hits (with location only), zip entries and backslashes, then `OK: <folder>` and `OK: <zip>` or `REFUSED: package removed.`

## 16. Key design decisions (summary)

- **Classic scripts, several files, UMD wrapper.** ES modules fail from file:// (2.2). A single hand-bundled file would also work offline, but it would stop Node from testing the exact same statistics code without a build step. Classic scripts keep one source of truth for the browser and the tests.
- **State in the URL hash only.** The hash makes plans shareable without a server, survives reloads, and keeps nothing in browser storage except the help flag. The encoding is base64url JSON, not query-style parameters, because the state has free text and a nested guardrail list.
- **Numerics.** Hart/West for the normal tails (precise small p-values), Acklam plus Halley for quantiles, and Lanczos plus Lentz continued fractions for t and chi-square (non-integer Welch df, accuracy far beyond the 1e-6 target).
- **Sample size.** The Fleiss et al. (ch. 4) normal approximation without continuity correction, because it is the textbook standard and the same closed form as R's `power.prop.test` default. The normal approximation for means is labelled, with its known small-n bias stated.
- **Intervals.** Wald for the difference and Katz log for the ratio, with explicit small-count warnings. More accurate score intervals (Newcombe) are in the backlog.
- **Verdict.** A strict precedence (SRM, then guardrail breach, then early analysis, then the statistical-vs-practical grid), so every verdict has one decisive reason and is reproducible.
- **Guardrails.** A breach means the observed degradation is beyond the limit; "At risk" means the interval reaches beyond it. The rule is stricter than a harm test and less strict than a non-inferiority test (6.9): it blocks observed regressions without requiring underpowered guardrails to prove non-inferiority.
- **Deny-list scan by file type.** Text is scanned as text, PNG metadata chunks are parsed and scanned, and compressed bytes are never scanned, so "0 hits" is reachable without weakening the matcher.
- **Peeking.** Warned about, never "corrected". The O'Brien-Fleming figure is informational, because a valid sequential analysis must be planned in advance.
